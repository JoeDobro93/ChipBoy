# ChipBoy parameters, in host order

Generated by `tools/demo/make_demo.py`. The order is the order
`Source/plugin/shared/Parameters.cpp` adds the parameters: the globals from
`addGlobalParameters`, then channels 1-4 from `addChannelParameters`, whose
per-kind conditionals decide which ids a channel has (only the wave channel
has Wave and Frame; only pulse channels have Duty; only PU1 has the sweep;
only NOI has LFSR). JUCE presents the list to VST3 hosts in exactly this
order; the wrapper's own Bypass parameter and, after it, its MIDI CC
emulation parameters follow the 85 below. `chipboy_paramdump` (a CMake target
of the plugin build) prints the same table from the running code, and
`make_demo.py --paramdump <path>` checks this file against it.

The **index** is what Reaper's `PARMENV` lines use. The **VST3 id** is what
JUCE derives from the id string (`String::hashCode()` with the top bit
cleared); Reaper writes it after the index (`index:id`) so an envelope
survives a change of order. Envelope values are normalised: for an
integer or choice parameter the stored value is `(v - min) / (max - min)`,
and the plugin rounds to the nearest step when it reads it back.

Per-channel parameters carry an extra position meaning "use the instrument's
value" (the top value of Level, Vibrato Depth, Envelope Volume/Rate, Sweep
Rate/Shift; the `inst` choice of Pan, Envelope Direction, Duty, Sweep
Direction, LFSR; 0 of Table, Wave, Vibrato Speed). Automation overrides the
instrument only where a lane is drawn away from that position.

The demo project automates: `ch1_source`, `ch3_keyswitch`, `ch4_keyswitch`,
`ch4_velocity`, `ch2_instrument`, `ch1_duty`, `ch2_env_rate`, `ch3_wave`,
`ch3_frame`, `master_l`, `master_r`, `declick`, `model`.
